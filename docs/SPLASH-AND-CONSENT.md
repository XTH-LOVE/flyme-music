# 开屏动画与用户协议同意书：方案

现状：**两者都不存在**。开屏方面 Tauri 没配 splash、Android 只有启动图标；协议方面只有登录页的勾选框，而应用不登录也能用 —— **匿名用户完全没被覆盖**。

---

## 一、开屏动画

### 关键认知：这是**两件事**，不是一件

| 层 | 谁负责 | 现在 |
|---|---|---|
| **系统启动画面** | Android 系统 | 默认白屏 + 应用图标 |
| **应用内开屏动画** | 你的 React 代码 | 不存在 |

**先做第一层。** 它决定"点图标到看见内容"这段是否突兀，而且**它是唯一能消除白屏的**。

### 1.1 系统启动画面（Android）

Android 12+ **强制**显示一个启动画面：应用图标 + `windowBackground`。你现在是默认值 —— **深色应用配白色背景，开屏会闪一下白**。

**要做的**：
- 在主题里把 `windowBackground` 设成与应用背景一致的 drawable（深色 + 居中的应用标记）
- 加 `androidx.core:core-splashscreen`，让 API 21–31 也走同一套（否则新老系统表现不一致）

**为什么值得**：成本很低（几个 XML + 一张图），但**白屏闪一下是最廉价的观感来源**。

### 1.2 应用内开屏动画

**核心问题不是"做什么动画"，是"什么时候结束"。**

绝大多数实现用**固定时长**（比如 2 秒）。这是错的：

- 快的设备上，2 秒是**凭空等待**
- 慢的设备上，2 秒后应用还没就绪，**照样看到未完成的界面**

**正确做法：绑定到真实就绪状态，设一个上限。**

就绪的判断应该包含：

```
字体加载完成          document.fonts.ready
持久化状态已恢复      store 从 localStorage 水合完成
播放引擎已创建        PlayerEngine 实例就绪
首屏已渲染            第一帧路由内容已挂载
```

**上限**：比如 2.5 秒。超时就淡出 —— 因为**卡在开屏比露出未完成的界面更糟**（用户会以为应用挂了）。

**动画本身**：应用标记从 96% 放大到 100% + 淡入，然后整体淡出。**不要做花哨的** —— 开屏是等待，不是表演，用户一天看几十次。

### 1.3 一个必须处理的坑

**开屏消失的瞬间，底下必须已经有东西。** 否则会看到"开屏 → 空 → 内容"三段闪烁。

做法：开屏盖在应用之上（`position: fixed` + 高 z-index），**等应用真正渲染完再淡出**，而不是先卸载开屏再看内容。

## 二、用户协议同意书

### 2.1 为什么不能只放在登录页

**你的应用不登录也能用。** 登录页那个勾选框只覆盖了注册用户，而**匿名用户一样会联网**（搜歌、播歌、AI、更新检查）—— 那才是隐私政策真正要说明的部分。

**所以需要一道首启门槛**，在进入主界面之前。

### 2.2 合规上必须满足的四点

| 要求 | 具体做法 |
|---|---|
| **先同意，后收集** | 门槛必须在任何网络请求之前。注意：更新检查也会联网，所以它也要在门槛之后 |
| **明示同意** | 必须是**勾选框 + 主动点击按钮**。"继续使用即表示同意"这类**不算** |
| **可拒绝** | 拒绝后必须真的有出路，不能死循环 |
| **可追溯** | 记录**同意的版本号 + 时间**，不是存一个布尔值 |

### 2.3 拒绝之后怎么办

三种做法，我推荐第三种：

| 做法 | 问题 |
|---|---|
| 直接退出应用 | 粗暴，但合规 |
| 只让用本地音乐 | **最诚实** —— 本地播放不联网，确实不需要同意联网条款 |
| 弹窗循环 | ✗ 这是骚扰，不是同意 |

**推荐**：明确告诉用户"不同意就只能使用本地音乐"，并给两个按钮 —— **「仅使用本地音乐」/「退出」**。

**理由**：它把选择说清楚了，而不是用"不同意就滚"逼人点同意。**后者拿到的同意是无效的**，法律上不成立。

### 2.4 文案不要写成法律文书

你的隐私政策里写得很清楚：**数据基本留在本机，联网只发生在六种情况**（音源搜索播放、封面、更新检查、AI、账号、一起听）。

**同意书上应该直接说这件事**，而不是堆一段没人读的条款：

> **我们不会上传你的歌单、收藏和播放记录** —— 它们只存在这台设备上。
>
> 使用在线播放、AI 解读等功能时，应用需要联网，具体见《隐私政策》。

然后下面是《用户协议》《隐私政策》两个可点开的链接（**复用已有的 `LegalSection`**，文档已经写好了）。

**为什么这样写**：一段"我们如何如何"的模板文案，用户只会直接划过去点同意。**说清楚"你失去什么、保留什么"，才是真的在征求意见。**

### 2.5 版本变更时重新征求

存的是**版本号**（比如 `2026-09-21`），不是 `true`。

政策更新后，老用户下次启动会**再看到一次**同意书。这是必须的 —— 否则你无法证明用户同意了新版本。

**注意**：不要因为小改动就重新弹（会被当成骚扰）。只在**实质性变更**时改版本号。

## 三、两者的顺序关系

```
点图标
  ↓
系统启动画面（Android 原生，无白屏）
  ↓
应用内开屏（等应用就绪，上限 2.5s）
  ↓
协议同意门槛（首次或政策变更后）
  ↓
主界面
```

**注意开屏在同意书之前** —— 开屏不需要联网，也不收集任何信息，所以它先出现是合规的。**而更新检查必须在同意书之后**。

---

## 四、我建议的推进顺序

**第一步：系统启动画面**（Android 原生）
- 成本最低，消除白屏，立刻可见
- 纯配置 + 一张图，无逻辑风险

**第二步：协议同意门槛**
- 合规必需，而且逻辑独立、容易验证
- 复用已有的 `LegalSection` 文档，不用新写内容

**第三步：应用内开屏动画**
- 放最后，因为它依赖"就绪状态"的定义 —— 而那个定义需要先看清楚应用启动时到底在等什么

---

## 五、需要你定的两件事

1. **拒绝同意后，是"仅本地音乐"还是"退出应用"？** 我推荐前者 —— 它更诚实，拿到的同意也更有效。
2. **开屏动画要多克制？** 我建议只做"标记淡入 + 整体淡出"，不做 Logo 动画。**开屏是等待，不是表演。**

---

## 附：这个方案刻意没做的

- **没有提议做复杂动画**（粒子、Logo 变形）—— 开屏一天看几十次，花哨的动画第三次就会烦
- **没有把同意书做成滚动到底才能点同意** —— 那是逼人，不是征求
