# AI 伴听与手机端 UI 改造方案

调研基于当前代码：`src/components/ai/AiCompanion.tsx`（290 行）、`ai.css`（350 行）、`src/layouts/layout.css`、以及今天修掉的几处移动端问题。

---

## 一、先说两个诊断

### 1. 移动端的问题不是「某个页面没调好」，是**没有统一策略**

断点有 **6 个不同的值**：

| 断点 | 出现次数 |
|---|---|
| `max-width: 560px` | 6 |
| `max-width: 959px` | 5 |
| `max-width: 640px` | 3 |
| `max-width: 900px` | 2 |
| `max-width: 960px` | 1 |
| `max-width: 720px` | 1 |

**这是今天所有移动端问题的共同根源。** 每个页面各自挑了一个断点，所以：

- 560 和 640 之间（比如 600px 宽）处于**两个规则都生效或都不生效**的模糊区
- 960 和 959 只差 1px，实际是同一个意图的两种写法
- 今天修的「歌名截断」只改了 `560px` 那一处，**其他断点下的同类问题没被覆盖**

**在逐个改页面之前，先把断点收敛成一套。** 否则每修一个页面，都会在别的宽度下留下新的不一致。

**建议的三档**（移动优先）：

| 名称 | 范围 | 含义 |
|---|---|---|
| `--bp-compact` | `< 600px` | 手机竖屏。底部导航、单列、安全区全开 |
| `--bp-medium` | `600–1023px` | 手机横屏 / 小平板。双列、侧栏收窄 |
| `--bp-wide` | `≥ 1024px` | 桌面。完整侧栏 + 多列 |

三档足够覆盖音乐播放器的所有形态，且**每一档都有明确的物理含义**（竖屏手机 / 横屏 / 桌面），不是随手取的数。

### 2. 今天暴露的移动端问题，都是同一类

| 现象 | 根因 |
|---|---|
| 顶部压到状态栏 | 只处理了 `safe-area-inset-bottom`，顶部一处没处理 |
| 迷你播放器与导航重叠 2px | 两个固定元素的占位区间没人算过 |
| 歌名截断 | 一行挤了封面/序号/时长/两个按钮，标题只剩 115px |
| 歌词卡顿 | 每次切行都做全量工作（滚动 + 全部行的样式） |

**共同点：布局是「各自为政」拼出来的，没有一份「屏幕上有哪些固定层、各占多少」的定义。**

## 二、AI 伴听 UI/UX 改造

### 现状

结构是：`.ai-panel`（head / body / input / actions）+ `.ai-msg`（ai / user / error）+ `.ai-empty` + `.ai-orb` + `.ai-chip`。

也就是一个**标准聊天面板**。问题是：**它长得像聊天软件，而不像「伴听」。**

「伴听」的核心场景是**一边听歌一边看 AI 说话**，而不是盯着对话框打字。当前形态要求用户：

1. 打开一个占屏的面板
2. 遮住正在播放的界面
3. 打字
4. 等回复

**这和「伴听」这个词的意思正好相反。**

### 改造方向：从「聊天框」变成「在场感」

**方案 A（推荐）：不打断的伴听层**

- **不再是全屏面板**，而是播放页上方的**一层轻量卡片流**。AI 的话以卡片形式从下方浮出，几秒后缩成一行，不遮挡封面与歌词。
- **默认不需要打字**。播到某首歌时 AI 主动说一句（基于当前歌曲 + 你的听歌偏好），你只需要**点赞 / 踩 / 换一个**——三个按钮，不用键盘。
- **想深聊再展开**。点卡片展开成完整对话面板（复用现有 `.ai-panel`，不必重写）。
- **光球（`.ai-orb`）改成状态指示**：不说话时是安静的呼吸，说话时有节奏——让「AI 在场」变成**余光可感知**，而不是需要打开一个界面。

**为什么这样改**：伴听的价值是「陪着你」，不是「等你来问」。现在的形态把 AI 变成了一个需要主动打开的功能，而它的正确位置是**背景里的一层**。

**方案 B（保守）：保留面板，只改体验**

- 面板改成**可拖拽的半屏 sheet**，默认半屏，不遮封面
- 输入框上方加**快捷意图**（「这首歌什么来头」「换首类似的」「这歌词什么意思」）—— 降低打字负担
- 消息流加**时间轴锚点**：每条 AI 消息标注它是在哪首歌、哪一句歌词时说的，点一下能跳回那个时刻

方案 B 改动小，但**没有解决「面板遮住播放界面」这个根本矛盾**。

### 具体要动的地方

| 现在 | 改成 |
|---|---|
| `.ai-panel` 全屏面板 | 默认收起，展开时是**不遮封面的半屏 sheet** |
| 每条消息都是气泡 | AI 的话是**卡片**（可点赞/踩/换），用户的话仍是气泡 |
| 只能打字 | 增加**三个默认动作**（赞 / 踩 / 换一个） |
| `.ai-orb` 装饰 | **状态指示**：静默呼吸 / 说话律动 |
| 无上下文 | 每条消息标注**触发时在听什么**（歌名 + 歌词行） |

## 三、手机端 UI 改造

### 第一步：先立规矩（不做视觉改动）

**1. 断点收敛到三档**（见上），把所有 `max-width` 查询替换掉。

**2. 定义「固定层预算」** —— 屏幕底部最多三个固定元素，各自的占位要**算出来**而不是猜：

```
底部安全区  env(safe-area-inset-bottom)
导航胶囊    62px，位于 bottom: 10px
迷你播放器  62px，位于 bottom: 86px   ← 今天修好的值
内容区底部内边距 ≥ 150px
```

把这三个数写成 CSS 变量（`--nav-height` / `--mini-player-height` / `--bottom-stack`），**任何新的底部元素都必须用它们计算位置**。今天那个「重叠 2px」就是没人算过。

**3. 安全区四边都处理**，不只是底部。加在**非滚动容器**上（今天踩过：加在滚动容器上 inset 会随内容滚走）。

### 第二步：逐页收口

按「用户碰得最多」排序：

| 优先级 | 页面 | 要解决 |
|---|---|---|
| 1 | **播放页** | 歌词可读性、封面与控件的比例、单手握持时按钮在拇指区 |
| 2 | **列表页**（歌单/搜索/我的） | 行内元素太多（今天已删序号+收紧间距，但需要统一的行高规范） |
| 3 | **「我的」页** | 今天删了假数据，剩下的标签需要重新审视信息层级 |
| 4 | **AI 伴听** | 见上 |

### 第三步：一次「宽度巡检」

三档断点定好后，在 **360 / 414 / 600 / 768 / 1024 / 1280** 六个宽度各过一遍全部页面。

**这一步不能省** —— 今天所有问题都是「在某个宽度下」才出现的，而我没法在设备上看到它们。

## 四、我建议的推进顺序

**不要一次全改。** 分三步，每步都能独立验证：

**第一步（小、能验证）：断点收敛 + 固定层预算**
- 只改 CSS，不动结构
- 结果：视觉几乎无变化，但后续每个改动都有了统一的基准

**第二步：AI 伴听改造成「不打断的伴听层」**
- 这是体验上收益最大的一项
- 风险：需要改交互，不只是样式

**第三步：逐页收口**
- 按上表优先级，一次一页

---

## 五、我需要你定的三件事

1. **AI 伴听走方案 A 还是 B？** 我推荐 A —— 但 A 会改变交互习惯（默认不打字），你需要接受这一点。
2. **断点三档的具体数值**，我建议 `< 600` / `600–1023` / `≥ 1024`。如果你的目标机型有特殊性（比如主要面向大屏折叠机），告我。
3. **「固定层」最多允许几个？** 现在是「导航 + 迷你播放器」两个。如果将来要加「桌面歌词入口」之类的，得先决定上限，否则底部会越来越挤。

## 附：这份方案刻意没做的事

- **没有列「把圆角从 12 改成 16」这类视觉细节** —— 那些应该在结构定下来之后再做，否则是给一个歪的骨架刷漆。
- **没有承诺时间** —— 每步的验证都要靠你在真机上看，我这边看不到。
